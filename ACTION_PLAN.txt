1. EXECUTIVE SUMMARY & REPOSITORY AUDIT
================================================================================
The current repository contains an initial functional scaffold:
- Backend: FastAPI + SQLite + Python 3.14 with endpoints for projects, tasks,
  commitments, schedule, settings, and AI extraction. Basic tests pass.
- Frontend: Vite + React 19 + TypeScript + Tailwind CSS with views for
  Calendar, Projects, Tasks, and Settings. Compiles cleanly.
- Design Assets: Found in `stitch_monolith_brutalist_operating_system/` containing
  comprehensive brutalist designs, CSS variables, typography (Chivo, JetBrains Mono,
  Space Mono), palette tokens (Acid Lime #c5ff42, Void Black #0d0f12, slate, etc.),
  and complete HTML/Tailwind reference implementations for:
    - Monolith Expanded Temporal Matrix Calendar (Hyprland / dotfiles waybar)
    - Monolith Project Lab Architecture Trace
    - Monolith Core Telemetry Workspace

While the application compiles and runs, it falls short of the `instructions.txt`
specification in several critical areas:
1. Visual aesthetic: The current frontend uses basic black-and-white default styles
   and generic `react-big-calendar` without the brutalist Swiss typography,
   Waybar status header, or dotfiles styling established in the design specs.
2. Scheduler limitations:
   - Does not prioritize urgent tasks before deadlines in topological sort.
   - Breaks between sessions are disabled (`if False`).
   - Daily workload limits ignore fixed commitments (only count tasks).
   - Dependencies only enforce same-day date constraints, not datetime sequence.
   - Non-splittable tasks are forced through splitting anyway.
   - Conflict detection does not provide rich diagnostic explanations.
3. Missing UIs:
   - Commitments (university classes, fixed weekly routines) have no frontend UI!
   - Course session generator (Scenario A) has a backend model stub but no endpoint or UI.
   - Unscheduled tasks have no dedicated triage panel or conflict explanation view.
   - AI planning shows raw unformatted JSON instead of structured interactive cards.
   - No offline command parser for natural language when AI is unconfigured.
4. Testing: Only 2 trivial unit tests exist; none of Scenarios A-F are validated.

2.2 The Scheduling Engine (Rules 1-13 & Deterministic Behavior)
--------------------------------------------------------------
- Instructions specify:
  * Rule 1-2: Respect fixed commitments, unavailable time, working hours.
  * Rule 3-4: Schedule tasks before deadlines whenever possible, prioritized by urgency.
  * Rule 5: Respect dependencies: dependent tasks start strictly after prerequisite end.
  * Rule 6: Respect preferred days and recurring routines.
  * Rule 7-8: Respect splittable flag, minimum and maximum session durations.
  * Rule 9: Include minimum breaks between demanding sessions.
  * Rule 10-12: Cap daily workloads (including commitments + tasks), preserve free time,
    spread long-term work across available days.
  * Rule 13: Never silently discard tasks; provide transparent reasons for placement
    and explicit explanations for conflicts.
- Current Status:
  * `app/scheduler.py` has several bugs and simplifications:
    - `split_sessions` ignores `task.get("splittable", True)`.
    - `daily_used[day]` only sums task durations, ignoring fixed university commitments.
    - Break calculation is disabled via `(min_break if False else 0)`.
    - Priority and deadlines are completely ignored during scheduling order (only topo_sort).
    - Dependent task earliest start uses `.date()`, allowing a dependent task to be
      scheduled earlier in the day than its prerequisite.
    - No check whether a found slot is actually *before* the task deadline.
- Solution:
  * Rewrite `scheduler.py` to enforce all 13 rules rigorously.
  * Count commitment hours toward daily capacity.
  * Calculate minimum breaks between consecutive sessions.
  * Sort topo-compatible tasks by (has_deadline, deadline_dt, priority).
  * Enforce deadline constraints during slot search; if impossible, record exact conflict
    reason in `unscheduled` diagnostics.

    preferred days, and durations.

    "Reduce session duration").

2.6 Rescheduling & Session Invalidation (Scenarios D & E)
---------------------------------------------------------
- Instructions specify (Scenarios D & E):
  * Missed session (Scenario D): user misses a session -> app offers to reschedule
    remaining work while preserving completed sessions and fixed commitments.
  * Changing availability (Scenario E): make Wednesdays unavailable -> future flexible
    activities recalculated and preview shows what changed.
- Current Status:
  * `/schedule/generate` and `/schedule/apply` delete all future non-locked blocks
    and re-run, but there is no diff summary showing what moved, and no dedicated
    "Reschedule Missed Sessions" action.
- Solution:
  * Implement schedule diffing: compare previous schedule with new schedule to return
    `{ moved: [...], unchanged: [...], newly_unscheduled: [...] }`.
  * Add "Reschedule Overdue / Missed Sessions" button in calendar status bar.
  * Ensure completed tasks, skipped tasks, and locked activities remain immutably fixed.
