We are now in the refinement/debugging phase of MONOLITH.

Do NOT rebuild the application or replace the existing visual design.

The current MONOLITH visual identity is intentional and should be preserved:
- Experimental brutalism.
- MONOLITH typography.
- Dark architectural interface.
- Lime accent.
- Dotfiles / Hyprland-inspired calendar.
- Dense technical metadata.
- Asymmetric composition.
- Terminal/status-bar influence.

The current UI is visually strong. The main problems are usability, configuration layout, and AI planning reliability.

## 1. FIRST: AUDIT THE EXISTING IMPLEMENTATION

Before changing code:

1. Inspect the entire frontend AI integration.
2. Inspect the backend AI routes and provider adapters.
3. Inspect the scheduling engine.
4. Inspect the frontend API client.
5. Identify exactly what calls `/v1/models`.
6. Identify whether `/v1/models` is expected to exist or whether the frontend is incorrectly calling it.
7. Trace the complete AI planning flow:

Natural-language input
→ frontend request
→ backend AI endpoint
→ provider/model
→ structured extraction
→ planning
→ scheduling engine
→ proposal
→ preview
→ approval
→ application/database
→ calendar refresh.

Do not assume that because an endpoint exists in FastAPI that the complete flow works.

Use actual runtime tests and inspect network requests/errors.

## 2. FIX AI PLANNING END-TO-END

The natural-language planning interface is the most important functional feature of MONOLITH.

A user should be able to enter something like:

"I have an online class every Wednesday for the next 40 days. I need to finish a project within 10 days. It should take around 8 hours. I prefer shorter sessions. I also want to study Agentic AI every Saturday."

The application should:

1. Send the request to the configured AI provider.
2. Extract structured commitments, projects, tasks, deadlines, durations, preferences, and constraints.
3. Validate the structured output.
4. Pass scheduling decisions to the deterministic scheduling engine.
5. Generate a proposal.
6. Show the proposal to the user.
7. Allow approval.
8. Apply the proposal.
9. Refresh the calendar and related views.
10. Persist everything in SQLite.

Do not simulate any of these steps.

If AI is not configured, clearly show that AI is unavailable rather than pretending the operation succeeded.

## 3. AI PROVIDER CONFIGURATION

Audit the Gemini/OpenRouter configuration.

Verify:

- API key is actually read by the backend.
- Selected provider is actually used.
- Selected model is actually used.
- API errors are surfaced clearly.
- Invalid credentials are reported clearly.
- Provider status reflects the real connection state.
- API keys never reach frontend source bundles or browser-visible requests.

Do not hardcode model names or assume every model supports identical structured output/tool-calling capabilities.

The application must remain usable without AI.

## 4. INVESTIGATE /v1/models

The backend currently exposes its own `/ai/*` API but does not appear to expose `/v1/models`.

There are repeated frontend requests resulting in:

GET /health → 200
GET /v1/models → 404

Find the exact frontend code making the `/v1/models` request.

Determine why it exists.

If it is unnecessary, remove the request.

If it is required by the application's provider abstraction, implement the correct provider-independent solution rather than adding a meaningless endpoint just to suppress the 404.

Do not hide the error without understanding its source.

## 5. VERIFY TOOL CALLING

The backend contains AI tool endpoints.

Inspect `/ai/tools` and `/ai/tools/execute`.

Verify that the AI can actually perform controlled application operations such as:

- Reading calendar state.
- Reading projects.
- Reading tasks.
- Creating projects.
- Creating tasks.
- Creating commitments.
- Updating tasks.
- Completing tasks.
- Skipping tasks.
- Rescheduling work.
- Recalculating schedules.

The AI must not directly invent calendar timestamps.

The deterministic scheduling engine remains responsible for valid scheduling.

AI decides intent and requested operations.
Backend tools perform operations.
Scheduling engine determines valid placement.

## 6. TEST AUTONOMOUS PLANNING

Create automated tests for at least:

A. New project + deadline.

B. Recurring commitment + flexible project.

C. Course split across recurring study days.

D. Impossible deadline.

E. Existing fixed university commitment.

F. Follow-up request modifying an existing plan.

G. Missed session requiring rescheduling.

H. AI provider failure.

I. Invalid AI structured output.

J. Duplicate planning request.

The tests must verify actual database and scheduling behavior, not merely HTTP status codes.

## 7. UX REFINEMENT — DO NOT REDESIGN

Preserve the existing MONOLITH visual language.

Improve usability without turning it into a conventional SaaS dashboard.

### Buttons

Increase the practical click target of small controls.

Primary actions should be immediately recognizable.

Do not rely exclusively on tiny typography or subtle borders to indicate interactivity.

Keep the visual style compact and brutalist while making controls comfortable to click.

Important actions such as PLAN, SAVE, APPROVE, COMPLETE, MOVE and RESCHEDULE should have clearly distinguishable interaction states.

### Navigation

Make the major application areas easy to discover and switch between.

Users should not have to hunt for important actions.

Preserve the technical status-bar aesthetic.

### Calendar

Keep the current calendar composition.

Do not replace it with a generic calendar component or SaaS dashboard.

Improve:
- Navigation clarity.
- Button hit areas.
- Active states.
- Hover states.
- Event interaction.
- Accessibility.
- Readability.

Maintain the dotfiles / Hyprland-inspired visual character.

## 8. CONFIGURATION PAGE REWORK

The current configuration page feels visually disconnected from the rest of MONOLITH.

Keep the same typography, colors, borders, and brutalist language, but redesign the information architecture.

Reduce the feeling of a single narrow form floating inside a huge empty page.

Organize settings into clearly defined architectural sections:

- Availability.
- Scheduling.
- AI Provider.
- Data / Storage.

Use the available screen space intelligently.

Do not simply make the form wider.

Make related settings visually grouped and easier to scan.

The AI configuration should make it obvious:
- Which provider is active.
- Which model is selected.
- Whether the provider is connected.
- Where the API key belongs.
- Whether AI is currently available.

Destructive actions such as database wipe must remain visually distinct and require confirmation.

## 9. INTERACTION PRINCIPLE

Follow this rule throughout the application:

"Visually unconventional. Functionally obvious."

MONOLITH should feel like an extremely customized Linux desktop environment, but a user should still immediately understand what is clickable, what is editable, what is informational, and what will change their data.

Do not make controls tiny merely to preserve the aesthetic.

## 10. RESPONSIVE / ACCESSIBILITY CHECK

Test the application at realistic desktop sizes.

Ensure:
- Buttons have usable click targets.
- Text does not become unreadable.
- Important controls remain accessible.
- Panels do not overlap.
- Calendar interactions remain usable.
- Keyboard navigation works for important actions where practical.

Do not sacrifice the desktop MONOLITH aesthetic to achieve generic responsive behavior.

## 11. IMPORTANT IMPLEMENTATION RULE

Do not rewrite working systems just because they could be implemented differently.

Inspect first.

Reuse existing architecture.

Fix the smallest necessary layer.

Do not introduce unnecessary dependencies.

Do not replace the current visual identity.

Do not generate mock AI responses.

Do not create fake calendar operations.

Do not declare AI functionality complete until an actual natural-language request has successfully gone through the complete pipeline and produced persistent calendar changes.

## 12. DEFINITION OF DONE

The refinement is complete only when:

1. I can enter a natural-language planning request.
2. The configured AI provider actually processes it.
3. Structured information is extracted.
4. The scheduling engine generates a realistic schedule.
5. I can preview the proposed changes.
6. I can approve them.
7. The changes persist in SQLite.
8. The calendar updates immediately.
9. Follow-up instructions can modify the existing plan.
10. AI failures are clearly reported.
11. The repeated `/v1/models` 404 has been understood and either correctly resolved or intentionally removed.
12. The UI remains recognizably MONOLITH.
13. Buttons and interactive controls are easier to use.
14. The configuration page feels like part of MONOLITH rather than a generic settings form.
15. Existing functionality and data are not unnecessarily broken.

After implementation, run the application and perform the end-to-end tests yourself. Report which tests passed and which remain unresolved.
